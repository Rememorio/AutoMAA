# 每周定时运行

每个自动化方案都可以拥有自己的 macOS LaunchAgent 和独立周计划。一个方案可以在不同星期使用不同时间，同时保留手动运行入口。

只有在对应方案已经有人值守地完整跑通后，才建议启用定时。

## 启用条件

- AutoMAA 主窗口可以关闭；每个已启用方案都由独立的 `AutoMAARunner` 在后台启动。
- 用户保持登录状态，并为 PlayCover 保留可交互的图形会话；不要注销、切换到登录窗口，建议不要停留在锁屏界面。
- 若要在设定时间准时开始，Mac 必须保持系统唤醒。显示器可以单独熄灭，但需要开启“显示器关闭时防止自动进入睡眠”，避免把息屏同时变成系统睡眠。
- Mac 没有关机。到点时如果系统已经睡眠，`StartCalendarInterval` 通常会在唤醒后补触发，而不是保证原定时间运行；关机期间错过的运行不会补回。
- 游戏无需更新、重新登录、验证码或协议确认。
- `maa-cli`、游戏 App、Bundle Identifier 和连接地址保持有效。
- 官服、Bilibili、繁中服与 MaaCore v6.16.8 起的韩服多账号匹配片段已经过人工验证；国际服和日服只启用一个账号且游戏保持该账号已登录。

| 到点时的状态 | 预期行为 |
| --- | --- |
| AutoMAA 已退出，用户已登录且 Mac 唤醒 | 后台 Runner 正常启动 |
| 显示器已熄灭，但系统没有睡眠 | 可以运行 |
| 屏幕已锁定 | LaunchAgent 可能启动，但 PlayCover 的图形操作不保证可用，不建议依赖 |
| 系统睡眠或 MacBook 合盖进入睡眠 | 不能保证准时；一般在系统完全唤醒后补触发 |
| 用户已注销或 Mac 已关机 | 不会运行；关机期间错过的任务不会补回 |

如果希望无人值守任务准时运行，建议接通电源，并在“系统设置 → 电池 → 选项”（台式 Mac 为“节能”）中开启“显示器关闭时防止自动进入睡眠”。不需要让屏幕一直亮着，也不要把“网络访问唤醒”或 Power Nap 当作可交互游戏自动化的保证。可对照 [Apple 的睡眠设置说明](https://support.apple.com/guide/mac-help/mchle41a6ccd/mac)和 [`StartCalendarInterval` 行为](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)。

Runner 启动后会使用 `caffeinate` 防止流程中途自动休眠；它无法阻止 Mac 在触发前已经进入睡眠，因此不能替代上述系统设置。

## 为方案设置时间

1. 在侧边栏打开要定时的自动化方案。
2. 在“定时运行”卡片中为时段选择星期并设置时间。
3. 如需让同一方案在其他星期使用不同时间，先从现有时段取消这些星期，再点击“添加时段”。
4. 开启开关。

新配置中的“轻量日常”默认是每天 09:00，“完整日常”默认是每天 21:00。已启用方案修改星期或时间后会自动同步，无需再次确认。界面显示“已启用”后，这个方案的配置才真正生效；关闭开关只卸载当前方案的 LaunchAgent，不影响其他方案。

同一方案的一周中，每个星期几最多只能属于一个时段，因为完成记录按“自然日 + 方案”保存；如果同一天再次触发相同方案，已成功步骤会被当天断点跳过。一天内需要执行不同内容时，应创建两个方案，例如“周日剿灭”和“完整日常”。

不同方案只有在星期和时间都相同时才冲突。周一 09:00 与周日 09:00 可以同时保存；两个方案都设置周日 09:00 时，AutoMAA 会在启用或修改时直接提示冲突，避免两个 Runner 同时争抢进程锁。

例如，可以这样安排一周：

| 方案 | 星期 | 时间 |
| --- | --- | --- |
| 正常计划 | 周一至周六 | 09:00 |
| 正常计划 | 周日 | 21:00 |
| 周日剿灭 | 周日 | 09:00 |

“周日剿灭”与“正常计划”使用不同方案 ID，因此上午完成剿灭不会让晚间正常计划误跳过同名步骤。不过，当晚方案若使用 MAA 的“游戏当前/上次”，游戏最近作战仍可能是剿灭；建议把正常计划的关卡策略设为“上次成功的常规关卡”或固定关卡。前者按账号保存最近一次实际成功的非剿灭关卡，剿灭不会覆盖；没有可用记录时 AutoMAA 会在启动游戏前阻止运行。

## 多方案调度

每个 LaunchAgent 都用方案 UUID 启动无界面 Runner。Runner 只执行指定方案，不会根据当前界面选择或名称猜测。

AutoMAA 会阻止星期和时间完全重合的计划。即使时间不同，前一个方案仍可能尚未结束；进程锁只允许一个工作流运行，因此也应根据完整日常的实际耗时主动留出足够间隔，使客户端能够关闭并释放连接。

运行期间 Runner 会：

- 使用进程锁阻止两个 AutoMAA 流程同时执行；
- 使用 `caffeinate` 避免工作流中途休眠；
- 继续使用当前方案当天的断点；
- 将可读进度写入“活动记录”，并把完整输出写入 AutoMAA 的诊断日志目录。

定时运行不要求 AutoMAA 当时处于打开状态。在后台 Runner 执行期间打开 AutoMAA，或从其他 App 返回 AutoMAA 后，“自动化总览”和“活动记录”会持续同步当前阶段、累计进度与最新结果；后台任务结束前，主 App 会避让其他 MAA 操作和应用更新。

“全局设置”中的 MAA 核心与基础资源自动更新只会在主 App 打开时检查，不会由后台 Runner 另行触发。启用后，如果下一次定时方案将在 90 分钟内开始，维护检查会至少推迟到该定时点后的安全窗口；若方案届时仍在运行，进程锁会继续避让。

AutoMAA 更新后首次打开新版本时，会自动比较 Runner 的版本与构建身份，并重新注册已启用的定时任务，以刷新 macOS 的启动约束。若后台流程仍在运行，这一步会等待流程结束，不会中断当前任务。

## 重要通知

在“全局设置 → 重要通知”中开启开关并允许 macOS 通知权限后，手动运行和后台 Runner 都可以发送系统通知。AutoMAA 只通知以下需要用户采取行动或查看原因的结果：

- 公招发现 5★/6★、特殊标签或方案配置的保留标签；
- 客户端需要更新、登录或其他人工处理；
- 流程因安全原因中止，或有步骤最终失败。

普通成功完成与主动安全停止不会发送通知。通知正文只显示结果概括，不包含账号名称、识别标签、路径或具体错误；完整信息仍在“活动记录”中。macOS 的专注模式、定时摘要和单独的 AutoMAA 通知设置可能静音或延后横幅，但不会改变 AutoMAA 的活动记录。

公招提醒会在对应公招任务结束并解析出结果后立即发送，不需要等待整套方案收尾；流程中止、人工处理和最终失败仍在流程结束时汇总通知。已经即时送达的公招提醒不会在流程结束时重复发送。

权限必须在 AutoMAA 主 App 中主动开启一次，后台 Runner 不会自行弹出授权窗口。关闭主窗口不影响已经授权的重要通知；可使用“测试后台通知”验证定时 Runner 的实际投递链路。若通知未送达，原因会写入活动记录；若在系统设置中关闭了权限，回到 AutoMAA 后会显示当前状态和重新打开通知设置的入口。

## 游戏更新后的建议

大版本更新后先关闭相关方案的定时运行，手动启动每个服务器一次：

1. 完成游戏包体更新；
2. 等待数据下载和解压；
3. 处理公告、协议或重新登录；
4. 确认能进入登录页或主界面；
5. 手动跑一次对应方案，再恢复定时。

详见[游戏更新与人工处理](../troubleshooting/game-update)。
